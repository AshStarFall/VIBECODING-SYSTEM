# Contributing

## Standard

Contributions should make a future project more correct, useful, safe, or economical to build. Prefer a tested workflow or a small, annotated resource set over bulk imports. Keep provider-specific setup optional and clearly labeled.

## Adding a resource

1. Search the catalog for duplicates and equivalent alternatives.
2. Prefer the canonical upstream project or official documentation.
3. Explain when it helps, when it is unnecessary, its meaningful tradeoffs, and the expected setup/context burden.
4. Separate verified facts from a discovery lead. Check license and current status before recommending adoption.
5. Add a review date or explicitly state that the link is unverified; never imply continuous monitoring.

## Editing workflows

Use plain Markdown and portable language. Include prerequisites, inputs, outputs, stop conditions, and verification. Avoid assuming one coding agent, subscription, cloud vendor, or framework. Update the README navigation when adding a top-level workflow.

## Review checklist

- Does this duplicate an existing rule, resource, or template?
- Can an agent identify which project types and risks should load it?
- Are steps actionable and outcomes verifiable?
- Are security, privacy, cost, maintenance, and licensing caveats proportionate?
- Are links and relative paths valid?
